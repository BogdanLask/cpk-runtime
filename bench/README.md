# Benchmark harness

`cpkrt_bench` measures the public cpkrt paths against a generated CPK archive.
It is a regression and comparison tool, not a correctness test and not a
general-purpose storage benchmark.

## Build and generate a fixture

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCPKRT_BUILD_BENCHMARKS=ON
cmake --build build
python3 bench/make_bench_fixture.py /tmp/cpkrt-bench.cpk
```

The default fixture has 4,096 entries, four CRILAYLA entries, 4 KiB raw
entries, and 64 KiB decoded packed entries. It is deterministic and contains
only generated bytes.

Useful generator options:

```text
--entries N          total entries (default 4096)
--packed-count N     number of CRILAYLA entries (default 4)
--raw-size N         bytes per raw entry (default 4096)
--packed-size N      decoded bytes per packed entry (default 65536)
--packed-mode refs   CRILAYLA tokens: "refs" or "literal"
--seed N             payload byte seed
--base-id N          first numeric entry ID
```

A large index fixture can be generated without large payloads:

```sh
python3 bench/make_bench_fixture.py /tmp/cpkrt-index.cpk \
    --entries 20000 --packed-count 0 --raw-size 0
```

## Run

```sh
./build/cpkrt_bench /tmp/cpkrt-bench.cpk
./build/cpkrt_bench /tmp/cpkrt-bench.cpk --file
./build/cpkrt_bench /tmp/cpkrt-bench.cpk --file-only
```

Options:

```text
--index-iters N      index open/close repetitions (default 100)
--lookup-iters N     cpk_find calls (default 2,000,000)
--read-iters N       provider read/release repetitions (default 200)
--decode-iters N     direct CRILAYLA decodes (default 50)
--file                also benchmark the platform file adapter
--file-only           use only the file adapter, without loading the archive
--first               use the first matching entry instead of the largest
--id ID               benchmark this entry ID specifically (hex or decimal)
```

By default the harness picks the largest raw entry and the largest compressed
entry, because small entries mostly measure fixed overhead. Use `--first` for
the first entry of each kind, or `--id` to target a specific ID. The selected
sizes are printed before the results.

For large archives, use `--file-only` so the archive is never loaded into
memory, and lower the read and decode counts so the run stays short:

```sh
./build/cpkrt_bench archive.cpk --file-only --read-iters 3 --decode-iters 3
```

## What is measured

| Label | Path |
| --- | --- |
| `index_open` | Parse the header, TOC, and ITOC from an in-memory image. |
| `lookup` | Binary search by ID over the parsed entry list, with periodic misses. |
| `provider_raw` | Provider lookup, stored read, lease allocation, and release for a raw entry. |
| `provider_packed` | Same path plus CRILAYLA header validation and decode. |
| `provider_raw_into` | Caller-buffer fill of a raw entry: stored read into caller memory, no lease. |
| `provider_packed_into` | Caller-buffer fill of a packed entry: read into caller staging plus decode. |
| `crilayla_decode` | `crilayla_decode()` alone, with input and output preallocated. |
| `file_index_open` | `cpk_open()` using the platform positional-read adapter. |
| `file_provider_raw` | Provider read of a raw entry through the file adapter. |
| `file_provider_packed` | Provider read and decode through the file adapter. |
| `file_provider_raw_into` | Caller-buffer fill of a raw entry through the file adapter. |
| `file_provider_packed_into` | Caller-buffer fill and decode through the file adapter. |
| `file_crilayla_decode` | Decode only, with bytes read from the file adapter outside the timer. |

The provider benchmarks include allocation and release because that is the
cost of the public lease API. `crilayla_decode` deliberately excludes those
costs so decoder changes can be evaluated separately.

## Caveats

- The fixture is synthetic. It does not model a specific title's asset mix,
  compression ratio, or entry-size distribution.
- `--file` reads are usually served from the OS page cache after the first
  pass. Drop caches or use a cold-read methodology if cold I/O is the target.
- Numbers are meaningful when compared on the same machine, compiler, flags,
  and fixture. They are not cross-platform claims.
- The harness is single-threaded. It does not measure concurrent provider use,
  because the provider is documented as nonconcurrent.
- The `*_into` labels reuse caller-allocated buffers, so they measure the fill
  path exclusive of lease allocation and release.
- Sanitizer builds are useful for validity checks but are not representative
  performance builds.

## Example run

On one Linux x86_64 machine with GCC 11.4, four real archives with 1,283 to
10,294 entries produced roughly:

- index open: 0.7 to 2.3 ms
- lookup: 21 to 32 ns per `cpk_find` call over 1,000,000 calls
- packed provider read and decode: 310 to 1,050 MiB/s of decoded output
- direct CRILAYLA decode: 450 to 1,450 MiB/s of decoded output

These were single-machine, warm-cache runs with the largest entry selected per
archive. They are an illustration of the harness, not performance targets, and
they will vary with entry mix, storage, compiler, and CPU.
